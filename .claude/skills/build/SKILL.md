# build — 개발 루프

설계·개발 단계의 기본 작업 방식이다. Owner가 목표를 정하고, Claude가 계획·구현·테스트·수정·보고까지 한다.
Owner의 작업 규칙(v3.1, 프로젝트 `CLAUDE.md`)이 이 스킬보다 우선한다. Owner는 코딩 초보자이므로 용어는 처음 쓸 때 쉬운 설명을 붙인다.

실행 지시어: 만들어줘 / 개발해 / 구현해 / 수정해 / 추가해 / 해결해 / 코딩해 / 진행해
비실행 지시어(기획해 / 설계해 / 검토해 / 설명해 / 어떻게 할까 / 좋네 / 알겠어)에는 코드를 고치지 않고 답만 한다.

## 1. 준비 (읽기)
- `docs/SPEC.md`, `CLAUDE.md`, `NEXT_STEPS.md`, `docs/FEATURES.md`, `git status`, `git log --oneline -10`을 읽는다.
- **SPEC이 없거나 수락기준이 비어 있으면 코드를 쓰지 않는다.** 이번 작업의 수락기준 초안(확인할 수 있는 문장 3~7개)을 만들어 Owner에게 확인받는다.
- 작업 브랜치에 있지 않으면 새 브랜치를 만든다 (`git switch -c <짧은-이름>`). main에 바로 커밋하지 않는다.

## 2. 범위 확인 (1회만)
아래를 **5줄 이내**로 보여 주고 OK를 받는다. OK 뒤에는 "코딩 진행할까요?"를 묻지 않고 끝까지 진행한다.
```
만들 것: …
안 만들 것: …
리스크: …
꼭 필요한 질문: … (없으면 "없음")
작업 단위: ① … ② … ③ …
```
- 사소한 선택(이름, 폴더 위치, 무료 라이브러리 등)은 묻지 않고 합리적인 기본값으로 정한 뒤 보고에 적는다.
- 작업 중 Owner의 질문은 승인 취소도 새 승인도 아니다. "멈춰" / "중단해"만 멈춘다.

## 3. 루프 (작은 단위마다 반복)
한 단위 = 수락기준 하나 또는 그보다 작은 것. 한 번에 여러 기능을 섞지 않는다.

1. **테스트 먼저** — 이 단위가 맞는지 확인할 테스트를 쓰거나 고른다. 자동 테스트가 어려우면(화면 모양 등) 확인 방법(실제 실행, 캡처)을 정한다.
2. **구현** — 기존 코드·컴포넌트를 먼저 찾아 재사용한다. UI는 `design.md`와 `design/tokens.css`를 따른다.
3. **검사 실행** — 테스트·타입 검사·린트·빌드 중 있는 것을 실제로 돌린다 (`CLAUDE.md`의 "자주 쓰는 명령").
4. **실패하면 고친다** — 아래 "멈추는 규칙"을 따른다.
5. **커밋** — 통과하면 이 단위만 커밋한다. 메시지에 무엇을 왜 바꿨는지 적는다.
6. `docs/FEATURES.md`(기능 → 파일 지도)를 갱신하고, L2 판단(새 모듈, 구조 변경 등)은 `docs/DECISIONS.md`에 한 줄 남긴다.

중간 보고는 하지 않는다. 막혔을 때와 끝났을 때만 보고한다.

## 4. 멈추는 규칙
| 상황 | 할 일 |
|---|---|
| 같은 오류로 3번 실패 | 고치던 방법을 버리고 원인 가설을 다시 세운다 (오류 전문 다시 읽기, 재현 최소화, 관련 문서 확인) |
| 같은 오류로 5번 실패 | 멈춘다. `NEXT_STEPS.md`에 시도한 것·남은 가설을 적고 현황을 보고한다 |
| L3 작업이 필요 | 그 작업만 멈추고 묻는다. 나머지 단위는 계속한다 |
| 라이브러리·API 사용법이 불확실 | 공식 문서(Context7 MCP가 있으면 우선)로 확인한다. 존재하지 않는 API를 추측해서 쓰지 않는다 |

L3(승인 필수): 데이터 삭제, 핵심 기능 제거, 파일 4개 이상 구조 변경, 유료 서비스, 배포, push --force, 보안 약화, 키·개인정보 외부 전송, SPEC 밖 기능.

### 절대 하지 않는 것
- 테스트를 통과시키려고 테스트를 지우거나, `skip`/`xit`/`@pytest.mark.skip`을 붙이거나, 검사(린트·타입)를 끄거나, 기대값을 틀린 결과에 맞춰 바꾸는 것
- 돌려 보지 않은 테스트·빌드를 "통과"라고 쓰는 것
- SPEC에 없는 기능을 덤으로 추가하는 것 (아이디어는 보고의 "추가 개선 추천"에만)
- Owner의 파일을 묻지 않고 지우거나 덮어쓰는 것

## 5. 마무리
1. 전체 테스트·타입·린트·빌드를 한 번 더 돌려 회귀(전에 되던 기능이 망가짐)가 없는지 확인한다.
2. **`spec-reviewer` 에이전트**에게 수락기준 대조를 맡긴다. 구현한 쪽이 아닌 리뷰어의 결과를 그대로 보고에 싣는다.
   ❌가 있으면 고치고 다시 맡긴다. 못 고치면 COMPLETED라고 하지 않는다.
3. `CHANGELOG.md`(Owner 눈으로 쓴 변경 기록), `NEXT_STEPS.md`, `docs/FEATURES.md`, 필요하면 `CLAUDE.md`(자주 쓰는 명령)를 갱신하고 커밋한다.
4. 화면이 있는 기능을 출시하려면 `ship-check`로 이어 간다.

### 완료 상태 (셋 중 하나)
| 상태 | 언제 |
|---|---|
| **COMPLETED** | 수락기준 전부 ✅(리뷰어 확인), 검사 통과, 회귀 없음, 문서·커밋 완료 |
| **IMPLEMENTED — VERIFICATION PENDING** | 코드는 다 됐지만 확인 못 한 항목이 있음 (예: Windows 실기, 휴대폰 실기기) |
| **INCOMPLETE** | 수락기준 중 안 된 것이 있거나 5회 실패로 멈춤 |

## 6. 보고 형식
```markdown
## 결과: {상태}

### 구현 내용
| 수락기준 | 결과 | 근거 |
|---|---|---|

### 테스트 결과
| 검사 | 통과 | 실패 | 미확인(이유) |
|---|---|---|---|

### Git 커밋
- `abc1234` {메시지}

### 남은 문제
- {없으면 "없음"}

### 실행 방법
{명령은 한 칸(코드 블록)에 한 줄씩}

### 추가 개선 추천 (지시 전에는 구현하지 않음)
- {아이디어}
```
